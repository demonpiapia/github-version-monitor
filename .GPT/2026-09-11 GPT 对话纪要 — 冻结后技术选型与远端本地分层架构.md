## 2. 对话轮次纪要

### Round 1 — Owner `[确定]`（L1）

**诉求**：项目冻结。除功能外，本项目也是工作流与工程可靠度的验证载体。要求推荐更优质 / 成熟的同功能或同类项目用于学习。

### Round 2 — GPT `[确定]`（L3–379）

**核心判断**：不应把本项目归类为「依赖更新器」，应把「同功能」与「同思想」分开看。

两个流水线的本质差异：

```text
Renovate:
  依赖声明 → 解析 datasource → 找到可用版本 → 版本约束
          → update candidate → branch / PR → CI / merge

本项目:
  本地软件清单 → GitHub Release → 本地版本 vs 上游版本
             → yes/no → 后续自动升级软件
```

Renovate 值得学的四点：

| # | 点 | 与本项目映射 |
|---|---|---|
| ① | Datasource / Versioning 分离（「平台怎么拿版本」与「版本怎么比较」不混为一件事） | 现有 `queryStatus` + `Compare-Ver` 设计 |
| ② | 发现更新 / 执行更新分离：`Monitor → Candidate → Decision → Upgrade → Verify` | **v1.12 已站到第一层与第二层之间** |
| ③ | Dependency Dashboard：把已发现 / pending / 延迟 / approval / rejected-deferred 统一作为状态呈现，异常不直接触发动作 | 现有 `yes/no`、`review=true`、`API failure` |
| ④ | Minimum Release Age：新版本发布后等待 X 天再建议更新，降低供应链风险 | **发现最新版本 ≠ 立即升级** |

补充事实：Renovate 支持大量生态与包管理器，提供 Hosted / Self-hosted 两种模式。

**关键反直觉结论**：

> 本项目不应继续向 Renovate 方向膨胀。真正缺的不是更复杂的 Version Manager，而是一个极稳定的小型 **Upstream Release Detector**。v1.12 已足够承担前半段。

**落地建议**：以自身 Skill 为基准做能力对照表，识别「业界成熟做法」与「自创脑补」（维度见 [§3.6](#36-能力对照维度)）。

> 价值判断（GPT 原话）：做这张对照表，比再写 v1.13 价值更高。

### Round 4 — GPT `[确定]`（L381–873）

长文，12 节。核心：**认可两层拆分，并进一步简化**。要点按节提炼：

| 节 | 主张 |
|---|---|
| 总览 | 远端负责「事实采集」，本地负责「解释和决策」；比本地 Agent 直连几十个 GitHub repo 干净很多 |
| 一 | 进一步简化：本地对比可省略；Remote = Upstream truth，Local = Installed truth。程序是否安装、装在哪、实际运行版本只有本地知道 |
| 二 | 版本比较下沉为**确定性本地工具**（`software / version / path`），Agent 不承担复杂计算 |
| 三 | **远端输出必须是机器可解析的数据快照，不是自然语言报告** |
| 四 | v1.12 退役定位为 `release snapshot generator`，只做 `checklist → GitHub → output.md`；只要数据契约一致，未来可被成熟项目整体替换（直接呼应你的「不继续造车」） |
| 五 | Worker 直接用 GitHub Actions（cron + API + 写回 Git 天然契合） |
| 六 | `checklist` 为唯一配置源，新增软件 = 新增 item，不改代码 |
| 七 | snapshot 必须携带 `status`，否则本地会误信 `latest = 1.2.3` 为可信事实 |
| 八 | 远端减负：不再承担 localVersion / yes-no / isNew / isFlip / backup / run.lock / review / 复杂 Markdown 事务 |
| 九 | 本地 Agent 日任务固定 4 步；日报 → UPDATE candidates → 用户批准 → Upgrader |
| 十 | 本地不要 clone 仓库，直接 GET raw `output.md`（未来可换 `output.json`），接口不变 |
| 十一 | 最终推荐架构（见 [§4](#4-架构决策记录adr-摘要)） |
| 十二 | 迁移价值不在 SKILL-v1.12 的工程细节，而在已验证的设计原则（见 [§7](#7-沉淀的设计原则)） |

节二给出的判定示例：

```text
Remote:  VS Code 1.105.0 / 7-Zip 26.00 / Git 2.51.0
Local:   VS Code 1.104.2 / 7-Zip 26.00 / Git 2.50.1
Result:  VS Code UPDATE / 7-Zip SYNCED / Git UPDATE
```

定位句：**直接选成熟 GitHub release monitoring Action/项目当远端采集器，自己只维护 `checklist` 和 `output` 契约**。

## 3. 调研结论：同类 / 同类思想项目

> 来源：Round 2 / Round 6 中 GPT 陈述。维护状态、Stars、archived 日期等**未经本纪要独立核实**，见 [§9](#9-存疑点与未核实项)。

### 3.1 第一梯队

| 项目 | 定位 | 值得学什么 |
|---|---|---|
| `renovatebot/renovate` | 最成熟的「版本发现 → 决策 → 自动化」体系；支持大量生态与包管理器；Hosted / Self-hosted 双模式 | ① Datasource / Versioning 分离；② 发现更新与执行更新分离；③ Dependency Dashboard（状态呈现而非直接触发动作）；④ Minimum Release Age（发现 ≠ 立即升级） |

| `iamspido/github-release-monitor` | 与本项目功能层最像：监控 GitHub / GitLab / Codeberg release，后台定期检查，邮件 + Apprise 通知，self-hosted | 不看 UI，看：repository configuration / polling model / release identity / persistence / deduplication / notification boundary |

## 4. 架构决策记录（ADR 摘要）

| ID | 决策 | 理由 |
|---|---|---|
| ADR-1 | 拆为**远端采集**与**本地解释**两层 | 本地 Agent 直连几十个 repo 不干净；两层各自做简单的事 |
| ADR-2 | Remote = Upstream truth；Local = Installed truth | 程序是否安装、装在哪、实际运行版本，只有本地知道，远端不应感知 |
| ADR-3 | 版本比较下沉为确定性本地工具 | Agent 不承担复杂计算，只消费 `software/version/path` |
| ADR-4 | 远端输出**数据快照**，非自然语言报告 | 快照可被本地 Agent / 软件管理器 / 自动升级程序 / Web UI / 移动端共同消费 |
| ADR-5 | v1.12 退役为 `release snapshot generator` | 只要数据契约一致，未来可被成熟项目整体替换（对应「不继续造车」） |
| ADR-6 | Worker 用 GitHub Actions，不自建服务 | 任务天然是 cron + GitHub API + 写回 Git；`GITHUB_TOKEN` 直接可用 |
| ADR-7 | `checklist` 为唯一配置源 | 加软件 = 加 item，不改代码 |
| ADR-8 | snapshot 必带 `status` 字段 | 防止本地把失败态的 `latest` 当可信事实 |
| ADR-9 | 本地经 raw 文件 GET 拉取，不 clone 仓库 | 解耦存储实现，未来换 `output.json` 或换成熟 monitor，本地接口不变 |

### 推荐架构

```text
                        GitHub
                           │
                    ┌──────▼──────┐
                    │   Checklist │
                    └──────┬──────┘
                           │
                           ▼
                   GitHub Actions
                           │
                     GitHub REST API
                           │
                           ▼
                   release snapshot
                           │
                           ▼
                      output.md
                           │
              ┌────────────┴────────────┐
              │                         │
        Local Agent                Future Updater
              │                         │
     local installed versions    download / install
              │                         ▼
              └────────────────→ verification
```

职责边界（单一职责，互相不越界）：

```text
Remote          →  上游现在是什么版本？
Local Agent     →  我的机器是什么版本？哪些值得关注？
Future Updater  →  要不要升级？怎么升级？升级后是否成功？
```

三层链路：

```text
Monitor  →  Decision  →  Upgrade

日报 → UPDATE candidates → 用户批准 → Upgrader
```

## 11. Part II 轮次纪要

### Round 9 — Owner `[确定]`（addon L1–2）

**这是整段对话里最关键的一次需求变更。**

- 不止要 version，还要 **release note**；
- 动因：很多软件版本发布后标注「不建议用于生产环境」——版本规范不严谨是作者自由，但**这类版本不能更新**；
- **这就是始终坚持让 Agent 参与的根本原因**；
- 现状：Actions 能取版本号和推送，Owner 早知道；但此前没要求 Agent 取 release note，是**人肉点开链接判断**，偶尔 Agent 会自己去看；
- 诉求：Actions 把 release note **单独收集** → Agent 介入时同时给出「版本号情况 + 更新总结」，省去人肉点开与分析的时间；
- 下一步：不同平台 / 网站的监控也加入 Actions，**单独模块化设计**，先做 GitHub version checker。

### Round 10 — GPT `[确定]`（addon L3–252）


| D | 7.1.0 | 7.2.0 | security fix | 优先更新 |

| 11 | 本地消费：优先 raw 单文件，其次 `git pull` |
| 12 | Agent 输入 = Remote Snapshot + Local Installed；输出 `UPDATE / SYNCED / NOT INSTALLED / HOLD / REVIEW / REMOTE ERROR` |
| 13 | Release Note 分析关键词（12 项）；**「最新版本」≠「推荐升级版本」**（`Version changed = YES` 但 `Upgrade recommendation = HOLD`） |
| 14–15 | 多 Provider 扩展 + 未来 `output.json` 数据模型；**第一版不维护 md + json 双事实源** |
| 16 | **第一版负面清单**：AI summary / 本地版本 / 复杂 SemVer / 自动升级 / 下载 / 安装 / 回滚 / 多 provider / 数据库 / Web UI / 通知集成 / 复杂 retry / 复杂历史库 |
| 17 | 三阶段路线 + 最终五层 `Monitor → Understand → Decide → Upgrade → Verify` |
| 18 | 实施优先级：简单 > 可维护 > 可替换 > 可扩展（而非 功能数量 > 架构复杂度 > 测试数量） |

## 12. Part II 影响：对 Part I 结论的修订

### 12.1 修订清单

| # | Part I 结论 | Part II 修订 | 影响面 |
|---|---|---|---|
| C1 | 远端只采集 `repo/latest/published/url/status` | **新增 `release note`（body）+ `name` + `draft` + `prerelease`** | §5 数据契约 |
| C2 | 本地日报 4 类 | **6 类**：`UPDATE / SYNCED / NOT INSTALLED / HOLD / REVIEW / REMOTE ERROR` | §5.5 |
| C3 | status 枚举 7 个 | **8 个**，新增 `metadata_incomplete` | §5.2 |
| C4 | 选定 `BMayhew/version-checker` | **降级为仅参考 workflow**；改为三件套组合 | §6.2 |

| C8 | 未定义「正式版本」 | **明确 `draft=false && prerelease=false`**；不按 tag 名重排 | 新增 ADR-10 |

### 12.2 新增 ADR

| ID | 决策 | 理由 |
|---|---|---|
| ADR-10 | 正式版本 = `draft=false && prerelease=false` | 作者版本规范不严谨，tag 名不可信；以 API 字段为准 |
| ADR-11 | **远端禁止做 Release Note 分析 / AI 摘要** | Actions = 便宜稳定事实采集；Agent = 昂贵智能解释决策 |
| ADR-12 | snapshot 语义 = 状态快照，**不是升级建议** | 禁止在 `output.md` 写「推荐升级 / 有风险 / 建议等待」 |
| ADR-13 | 失败必须 `version: ""` + 明确 status，**不得回填旧版本伪装 ok** | 延续「失败不能伪装成功」 |
| ADR-14 | 第一版只做 GitHub 单 provider，但统一输出结构预留多 provider | 模块化：加 provider 不重设计系统 |
| ADR-15 | 第一版不维护 md + json 双事实源 | 单一事实源优先 |
