## 7. 发现的问题

### 7.1 P2 计数与缺陷描述不一致（轻微）

报告 L.2 说 `P2: 2`（T38 + T23），但 K.2 描述了 **3 个缺陷**：
- 缺陷 1: Step 4 Set-Content 无 try/catch（T38 发现）→ T38 FAIL → P2
- 缺陷 2: Step 5 Move-Item 无 try/catch（T23 发现）→ T23 FAIL → P2
- 缺陷 3: Step 5 Set-Content 无 try/catch（T22 发现）→ T22 **PASS** → **未计入 P2**

T22 和 T38 有相同缺陷（Set-Content 无 try/catch → 锁残留），但 T22 标记为 PASS 因为其测试标准只验证"主 md 不变"（未要求验证锁释放），而 T38 的标准包含 `RUN_STATUS|failed|`（锁释放相关）。

**影响**: 不影响 Verdict（即使 P2=3 也仍是 NOT_READY），但 P2 计数应注明"2 个测试 FAIL + 1 个测试 PASS 但存在同类缺陷"。

### 7.2 T22 测试标准宽松（测试设计层面）

T22（md 临时文件失败）与 T38（review 写回失败）有相同的根因（Set-Content 无 try/catch → 异常冒泡 → 锁残留），但：
- T22 计划标准：仅"主 md 不变" → PASS
- T38 计划标准：包含"RUN_STATUS|failed|" + 锁释放 → FAIL

建议 v1.9 验证将 T22 标准对齐 T38（增加锁释放验证）。

### 7.3 Phase 4 报告将 sub-agent 的 PARTIAL 转为 FAIL

Phase 2 sub-agent 报告 T38 为 "PARTIAL"（3/4 通过），Phase 4 sub-agent 报告 T23 为 "PARTIAL"。最终报告统一转为 FAIL。

计划只有 PASS/FAIL/BLOCKED 三态（无 PARTIAL），此转换合理。 ✅
