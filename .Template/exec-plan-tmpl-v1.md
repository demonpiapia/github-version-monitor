# 执行计划制定参考模板（exec-plan-tmpl-v1）

> **模板版本**: v1
> **提炼来源**: exec-plan-v1.9-a→e 五版迭代与三轮独立审计实战（2026-09-08）
> **适用范围**: 任何需要拆解为多阶段、由主 agent 协调单个 sub coding agent 串行执行的任务（验证/实现/重构/迁移/发布/修复）
> **使用方法**: 复制本模板 §1-§9 作为计划骨架 → 替换全部 `{{占位符}}` → 按附录 C 裁剪 → 用附录 A 自检清单逐项核对后定稿。附录 B 用于复查设计决策。

---

## 0. 模板结构总览

| 章节 | 作用 | 对应核心要素 |
|---|---|---|
| §1 计划头部 | 元信息与版本链 | 全程可追溯 |

| §3 全局机制 | 执行架构、隔离、接续、禁止事项 | 串行执行 + 任务可接续 |

## 1. 计划头部

```markdown
# {{任务名}} — 执行计划

> **版本**: exec-plan-{{标识符}}-{{字母}}（基于 exec-plan-{{标识符}}-{{前一版本字母}} 修订，采纳第 {{N}} 轮审计 {{审计项编号}}）
> **制定日期**: {{YYYY-MM-DD}}
> **依据**: {{唯一事实源文件的完整路径}}（唯一事实源）
> **被操作对象**: {{主对象文件/系统/服务}}
> **执行模式**: 单一 sub-agent 串行执行，禁止任何形式的多 sub-agent 并行
> **生产主运行环境**: {{OS + 运行时 + 具体版本}}
> **兼容/次要环境**: {{如适用；必须注明"不作为主环境"}}
> **修订记录**: 见 §9 修订日志
```

**头部规则**：

1. "依据"必须是可直接打开的具体文件；存在多个上游文档时，指定**唯一事实源**，其余列为"参考"。参考文档的结论不得作为判定依据（见附录 B P-04）。
2. 版本字母递增（a→b→c…）。**每次修订新开文件，禁止覆盖旧版**；修订来源（审计报告/变更请求）写进版本行。
3. 环境必须写实（已核实的版本号），不写"最新版"。

## 2. 任务定义

### 2.1 背景与输入基线

```markdown
{{前序轮次/版本的结论概述——仅信息参考}}
{{本次要解决的 {{N}} 个具体问题/目标，逐条列出，编号}}
```

**规则**：

- 列出的每个问题必须注明来源（上游事实源原文位置 / 旧报告结论 / 静态发现）。来源为旧报告的，须加脚注声明"仅供信息参考，不影响测试/实施设计决策（§2.3 独立性原则）"。
- 开工前采集**输入基线**：所有将被读取或修改的关键对象的指纹（SHA256/版本号/配置快照），保存为基线文件。

### 2.2 目标与完成定义（DoD）

```markdown
{{总目标}} 的唯一完成标准：

{{输入/异常/变更}}
        ↓
{{中间要求 1}}
        ↓
{{中间要求 2}}
        ↓
{{明确终态}}
        ↓
{{禁止出现的假成功}}
```

**规则**：完成定义必须是**可观察的终态描述**（输出什么、状态是什么、绝不出现什么），不是"做好/完成"这类不可判定表述。

### 2.3 事实源与独立性原则

```text
1. 所有设计决策必须基于两个事实源的直接阅读：
   - {{事实源 1：如被测/被改对象源码（行号 + 逻辑）}}
   - {{事实源 2：如上游任务书/需求原文}}
2. 旧轮次报告的结论不得直接作为本轮设计依据。
   旧发现只能作为"待独立验证的声明"。
3. 引用旧发现的，必须在执行阶段独立验证后才能作为事实采纳。
4. 旧报告的结论（PASS/FAIL/计数）仅供信息参考，
   不得影响本轮任何构造方法、验证项或判定逻辑。
5. 链式继承风险：A 引用 B 的结论、B 引用 C 的结论……
   最初版本的系统性偏差将沿链传播。本原则用于切断该链。
```

## 3. 全局机制（跨 Phase 通用约定）

### 3.1 执行架构（单 sub-agent 串行）

```text
Phase 0 (sub-agent) → 主 agent 审查 → Phase 1 (sub-agent) → 主 agent 审查 → … → Phase N-1 (sub-agent) → 主 agent 审查 → Phase N (主 agent 收尾)
```

- **严格串行**：下一 Phase 仅在上一 Phase 的主 agent 审查通过后启动。
- **单一 sub-agent**：每个 Phase 派遣且仅派遣一个 sub-agent。
- **禁止并行**：任何时刻最多一个 sub-agent 在运行。
- **sub-agent 任务规范**——每个 sub-agent 接收：任务规格（计划中该 Phase 完整描述）、关键对象绝对路径、证据要求清单、环境隔离指令、`resume_from` 参数（仅中断恢复时）；产出：证据文件、结构化结果摘要、`phase-progress.json`。

### 3.2 隔离与环境机制 [必填]

```markdown
所有工作通过 {{隔离机制，如环境变量重定向 / 工作目录副本 / feature 分支}} 实现：
- {{机制 1：如何保证不触碰生产对象}}
- {{机制 2：外部依赖如何替换（mock/stub/fixture），替换点的 contract 是什么}}

**替换体（mock/stub/fixture）规格要求** [P-13]：
- 逐场景列出返回对象/数据的成员名、取值、**类型**，并与真实消费方的访问路径逐一对齐（消费方代码行号）
- 替换体构造完成后、使用前，执行一次"contract → 消费方表达式"对齐自检，记录证据
- 优先选择无系统级变更的方案（进程内注入 > 配置劫持 > hosts/服务变更）
```

**构造方法可行性规则** [P-11]：计划中给出的每个构造方法选项，制定时逐个评估平台可行性；不可行的显式注明"不可作为构造方法"并说明原因（例：Windows 目录 `ReadOnly` 属性不阻止创建文件；`[System.IO.File]::Open()` 不能打开目录）。**有系统/环境变更的构造（ACL、注册表、hosts、服务）必须附带备份与还原步骤** [P-16]。

### 3.3 中断接续方案（任务可接续）

| 中断类型 | 检测方式 | 恢复策略 |
|---|---|---|
| 上游 API/服务调用失败 | sub-agent 无返回或返回错误 | 主 agent 重试同一 Phase，传入 `resume_from` 指向已完成步骤 |
| 外部依赖超时/失败 | 超时/异常 | 步骤内退避重试（max_retries={{N}}），仍失败则标 BLOCKED |
| 输出截断/不完整 | 返回不完整 | 主 agent 核验已产出证据文件，从断点继续 |
| sub-agent 上下文溢出 | 返回不完整 | 主 agent 核验已生成证据，拆分剩余工作到新 sub-agent |

**断点保存机制**：每个 Phase 完成后，sub-agent 在工作目录生成 `phase-progress.json`：

```json
{
  "phase": "Phase{{N}}",
  "start_time": "{{ISO8601}}",
  "end_time": "{{ISO8601}}",
  "status": "completed|partial|failed",
  "completed_steps": ["{{step1}}"],
  "pending_steps": [],
  "evidence_files": ["{{产出文件}}"],
  "next_phase": "Phase{{N+1}}"
}
```

**恢复原则**：sub-agent 无状态。恢复只依据产物文件 + progress 文件 + `resume_from`，不依赖任何会话记忆。

### 3.4 禁止事项 [按任务裁剪，但不可为空]

```text
1. 禁止修改 {{不可变对象，如规范文件/上游任务书}}
2. 禁止触碰 {{生产对象}} — 用 {{隔离方式}} 测试/操作
3. 禁止复用 {{旧产物}} 作为本轮 PASS 证据
4. 禁止修改 {{上游事实源文件}}
5. 禁止输出 {{secret 类信息}}
6. 禁止为使任务通过而修改 {{被操作对象}}
7. 禁止多 sub-agent 并行执行
8. 禁止 Verdict/结论由预期结果而非实际证据决定
```

### 3.5 执行模式 [必填]

- 所有脚本经 `{{运行时}} -NoProfile -NonInteractive -File <script> *>&1 > <output.txt>` 执行（后台静默，输出重定向到文件）。
- **进程模型声明** [P-01]：`-File` 模式下每个脚本独立进程，**脚本间无共享变量**。凡需"中途注入/在同进程内分段控制"的场景，必须设计同进程 harness（内联复制目标代码 + 明确注入点 + 受限 diff 验证），并说明为何其他方式（如 dot-source）不可行。
- 常驻辅助进程（监听/锁持有）用 `Start-Process -WindowStyle Hidden` 启动、测试后 `Stop-Process` 终止。

## 4. 模块化拆解

### 4.1 模块总览表 [必填]

| Phase | 模块名 | 输入 | 输出 | 优先级 |
|---|---|---|---|---|
| 0 | {{基线采集 + 环境准备}} | {{输入}} | {{产出清单摘要}} | 基础 |
| 1 | {{拆解/提取/准备}} | {{输入}} | {{产出}} | 基础 |
| 2..N-1 | {{核心工作模块，逐个列出}} | {{输入}} | {{产出}} | **硬门槛** / 关键 / 中 / 辅助 |
| N-1 | {{独立复核（self-review）}} | 全部前序证据 | 复核报告 | 质量控制 |
| N | {{汇总 + 收尾}} | 全部证据 | {{最终报告/发布物}} | 收尾 |

### 4.2 拆解规则

1. **输入封闭**：每个模块的输入只允许来自（a）事实源文件（b）已通过审查的前序 Phase 产出。模块间**只通过产物文件传递状态**，绝不通过 sub-agent 的会话记忆传递。
2. **输出清单化**：每个模块的产出是逐文件清单，可被审查点逐项核对。
3. **粒度**：单模块工作量 = 单个 sub-agent 一次会话可完成（上下文预算内）；超出则继续拆分。
4. **优先级语义**：硬门槛 = 失败即整体判定失败；关键 = 失败进入高风险复核；中/辅助 = 失败记录不阻断。硬门槛模块必须在计划中显式标注。
5. **第一模块固定为基线采集**（指纹 + 环境确认），**倒数第二模块固定为独立复核**，**最后模块固定为汇总收尾**（适用于 L/M 型；S 型见附录 C）。

## 5. Phase 详细规格（每阶段标准骨架）

每个 Phase 按以下骨架编写，缺一不可：

```markdown
### Phase {{N}}: {{模块名}}（{{优先级}}）

**前置条件**: 依赖 Phase {{X}} 的 {{具体产出文件}}；{{环境前提}}

**输入参数**:
- {{参数 1: 路径/值/来源}}
- {{参数 2}}

**处理逻辑**:
1. {{步骤——动词开头、可直接执行、含具体方法；方法选项逐个标明可行性}}
2. {{步骤}}
3. {{若含注入/分段/替换——写明精确位置（源行号）、注入内容、为什么其他方式不可行}}

**输出结果**（逐文件清单）:
- `{{路径 1}}` — {{用途}}
- `{{路径 2}}` — {{用途}}

**证据要求**:
- {{每项工作至少: 执行 stdout + stderr + 结论报告}}
- {{涉及文件变更: before/after 副本 + SHA256（写明指纹文件须覆盖哪些对象）}}
- {{涉及外部调用: 实际响应/状态码/计数}}
- {{涉及环境变更: 变更前快照 + 还原后验证}}

**主 agent 审查点**（全部满足才放行）:
- [ ] {{可判定检查——"确认 X 存在 / 等于 Y / 不包含 Z / 指纹一致"}}
- [ ] {{可判定检查——条件化的必须写明"仅当 {{条件}} 时验证"}}

**失败处理**: {{FAIL 时的动作：记录并继续 / 立即中止并标 BLOCKED / 回滚到 before}}
```

**骨架规则**：

1. 审查点禁止不可判定表述（"确认质量良好""确认正确性"），必须落为存在性/相等性/包含性/一致性检查。
2. 条件化期望必须显式标注条件（教训 P-10：验证项写"有 {{X}} 时"，审查点却把它当必查项，会误判）。
3. 步骤中引用的每个数量词、清单、状态集合，必须能指认事实源出处（P-07），枚举类必须列全项。
4. 方法选项中已被证伪的，保留原文并标注"不可行 + 原因"，防止后续执行者重试。

## 6. 分阶段验收

### 6.1 审查门流程

```text
sub-agent 完成 → 产出 phase-progress.json + 证据文件
→ 主 agent 审查（status=completed？证据逐项核对审查点？）
→ PASS → 启动下一 Phase
→ FAIL → 不启动下一 Phase；按该 Phase 失败处理规则：修复重试 / 回退 / 标 BLOCKED
```

### 6.2 审查规则

1. 主 agent 审查是**独立复核**，不是听取汇报：审查点要求核对的证据（stdout、指纹、清单），主 agent 亲自读取核对，不采信 sub-agent 的结论转述。
2. 审查点全部可判定；任一不满足 → 该 Phase 未通过。
3. 硬门槛 Phase 未通过 → 触发 §8 的整体判定规则（但仍完成后续 Phase 以保留完整证据，除非失败处理声明立即中止）。
4. **数字一致性**：所有计数类结论必须满足守恒式（如 Executed = PASS + FAIL + BLOCKED）；计划中同一数字只允许一个权威出处（优先引用清单，而非手抄数字）[P-09]。

### 6.3 独立复核模块（L/M 型必设）

倒数第二个 Phase 固定为独立复核（self-review），固定检查集：

```text
1. 操作对象是否被修改 — 重算指纹与基线比对
2. 旧证据是否被当作当前产出 — 核对证据目录归属
3. 输入/fixture 是否正确 — 逐项核实存在性与内容
4. 派生物是否被修改导致假结果 — 按 manifest 重算指纹；注入类派生物做受限 diff（仅允许计划声明的注入差异）
5. FAIL 是否被改写为 BLOCKED — 逐项核对实际输出 vs 结论
6. BLOCKED 是否被改写为 PASS — 同上
7. 报告数字是否一致 — 守恒式核算
8. 证据与结论是否矛盾 — 实际输出 vs 报告结论
9. {{基线对象完整性 — 重算指纹与开工基线比对}} [P-05]
```

## 7. 可追溯性机制

### 7.1 证据规则

| 情形 | 至少留存 |
|---|---|
| 每项执行 | stdout.txt、stderr.txt、test-report.md（或 work-report.md） |
| 涉及文件变更 | before/after 副本 + 指纹（sha256-before/after.txt，写明覆盖对象） |
| 涉及锁/状态/环境 | before/after 快照（额外中间态单独存档） |
| 涉及外部调用 | 实际响应、关键 header/字段、请求计数 |
| 环境变更 | 变更前快照 + 还原后验证记录 |

### 7.2 指纹与清单

1. **开工基线**：所有将被读取/修改的关键对象在 Phase 0 采集指纹。
2. **每个采集物必须有消费者** [P-05]：任何在开工时记录的指纹/快照，必须在后续某个 Phase 的审查点或复核模块中被复核比对；否则删除采集动作或补上复核环节，不留死数据。
3. **派生物必须有 manifest** [P-12]：从源文件提取/生成的派生物（脚本/配置/包），生成 manifest 记录"源文件指纹 + 源行号范围 + 派生物指纹"；复核时按 manifest 重算。注入类派生物（harness/包装器）做**受限 diff**：与源原文对照，仅允许计划声明的注入差异。
4. **禁止保存**：{{secret/token/凭证类}}。

### 7.3 口径与引用规则

1. 所有数量词（"{{N}} 项""共 {{X}} 条"）必须能指认事实源出处；**枚举类判断必须读取完整原文表格后列全项**，禁止仅凭关键词搜索结果下结论（搜索 pattern 覆盖不全 + 输出截断会导致漏项）[P-07]。
2. 旧报告/旧轮次结论只作信息参考；作设计依据前必须本轮独立验证并留存验证证据 [P-04]。
3. 引用其他章节/文档的规则，修改时**全文搜索所有引用点同步更新** [P-15]。
4. 计划与上游文档的格式要求冲突时（如结论模板加注），保持上游字面格式、以附注形式补充信息，并在修订日志声明该偏离 [P-17/D4 类]。

## 8. 判定与收尾

### 8.1 最终判定逻辑

**PRODUCTION_READY / {{成功终态}}** 必须同时满足：

```text
P0 = 0
P1 = 0
{{维度 1}} FAIL = 0
{{维度 1}} BLOCKED = 0

{{硬门槛清单逐项 PASS}}
{{结构性检查逐项 PASS}}
{{主环境判定 PASS}}
```

**{{失败终态}}**：任意 `P0 > 0 / P1 > 0 / {{维度 1}} FAIL > 0`，尤其 {{硬门槛清单}} 任一 FAIL。

**{{阻塞终态}}**：仅当 `P0 = 0 / P1 = 0 / {{维度 1}} FAIL = 0 / BLOCKED > 0`。

**判定规则**：

1. 若上游文档存在规则冲突（如"次要环境失败不阻塞"vs"任何 FAIL>0 即失败"），必须定义**计数维度**（如 production-critical vs compatibility）并声明裁决规则，禁止留双解 [P-02]。
2. 结论模板与上游格式对齐；需要补充口径信息时用后置附注，不改写字面格式。
3. FAIL 不得改写为 BLOCKED；BLOCKED 不得改写为 PASS；旧证据不得冒充新证据。

### 8.2 最终执行摘要模板 [逐项与实际安排映射]

```text
{{环境可用性 4 项}}
{{数据来源 2 项}}
{{逐测试/逐任务结果}}
```

**规则**：模板中的每一项必须映射到计划中实际安排的工作；若某项本轮未安排（如上游模板遗留），在报告 N 节显式声明"本轮未安排，依据为 {{历史轮/不适用}}"，不得留空或编造 [P-17]。

### 8.3 收尾动作

1. 汇总全部证据，生成最终报告（章节清单固定，逐节对应上游要求）。
2. 基线对象完整性复核（指纹比对）。
3. 入库：**commit 文件范围显式列出**（被操作对象、证据目录、报告、复核报告、本执行计划）[P-06]；commit message 必含：终态判定、分类计数、P0/P1/P2 计数、新增发现、新增证据路径。
4. 环境还原确认（§3.2 的还原步骤验证）。
